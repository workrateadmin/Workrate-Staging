WORKRATE — CREATE A SAFE STAGING ENVIRONMENT END TO END

GOAL:

Create a completely separate WorkRate staging environment so the release flow becomes:

DEVELOPMENT
→ STAGING
→ PRODUCTION

IMPORTANT:

The staging environment must contain the SAME CODEBASE as WorkRate, but must NOT contain:

- production customer data
- production database contents
- production secrets
- production Stripe live credentials
- production Meta/Vapi customer mappings
- production email delivery permissions
- production file storage
- production Clerk users
- production HMRC production credentials

Do NOT modify the current production WorkRate deployment.
Do NOT publish to production.
Do NOT copy Huntley Bespoke production data into staging.

13. STORAGE ISOLATION
==================================================

DO NOT let staging read/write the production file bucket.

This is critical.

Implement the existing Task #97 requirement:

“Prevent any test environment from reaching the production file bucket.”

Preferred:

separate staging storage bucket.

If a separate bucket is not practical yet:

use independently validated staging storage identity and fail startup if production storage is detected.

Do NOT rely solely on a folder prefix if production credentials still permit access to the production bucket.

Staging must not be able to:

- read production receipts
- read production job evidence
- read production documents
- overwrite production objects
- enumerate production objects
