==================================================
2. DEFINE THE SMALLEST GATEWAY
==================================================

Build the gateway as a very small standalone service.

Its only responsibility is:

1. receive an authenticated request from WorkRate
2. validate that request came from WorkRate
3. receive/derive truthful fraud-prevention network evidence
4. call HMRC sandbox
5. return the HMRC result safely to WorkRate

It is NOT:

- another WorkRate backend
- another tenant database
- another finance system
- customer-facing
- a general proxy
- a public API

Keep it minimal.

==================================================
5. WORKRATE → GATEWAY AUTHENTICATION
==================================================

Use the existing HMAC server-to-server model unless the audit finds a security flaw.

Requirements:

- strong shared secret
- timestamp
- nonce/request ID
- request signature
- replay protection
- constant-time signature comparison
- narrow clock tolerance
- idempotency support
- HTTPS only

Reject:

- missing signature
- invalid signature
- stale timestamp
- reused nonce where inappropriate
- malformed request

Never return authentication secrets to the browser.

==================================================
6. TOKEN HANDLING
==================================================

HMRC access/refresh tokens must remain server-side.

Determine the safest existing flow:

OPTION A:
WorkRate sends the current encrypted/server-resolved access token to the trusted gateway over the authenticated channel.

OR

OPTION B:
Gateway receives a short-lived WorkRate authorization reference and WorkRate resolves token usage another safe way.

Use the smallest secure approach compatible with existing architecture.

Never:

- expose HMRC token to browser
- persist tokens unnecessarily on the gateway
- log access tokens
- log refresh tokens

Prefer request-scoped token use.

==================================================
7. CLIENT NETWORK EVIDENCE
==================================================

This is the critical part.

Implement a truthful mechanism for the gateway to obtain required client/network evidence.

Current blocker includes:

- originating public client IP / verified forwarding chain
- browser public source port where required
- Gov-Vendor-Forwarded
- Gov-Vendor-Public-IP

Do NOT copy untrusted browser-supplied IP values into HMRC headers.

If HMRC requires the gateway to directly observe the browser connection:

build the smallest short-lived browser attestation mechanism.

Possible flow:

Browser
→ gateway attestation endpoint
→ gateway directly observes remote IP/source connection details
→ gateway issues short-lived signed attestation token
→ browser sends attestation token to WorkRate
→ WorkRate includes opaque attestation in HMRC preparation/submission request
→ gateway validates its own attestation
→ gateway uses the network evidence it previously observed

The attestation must:

- be short-lived
- contain or reference only necessary evidence
- be signed by the gateway
- be bound to a WorkRate user/business/session where practical
- be single-use or replay-resistant where required
- never trust browser claims about IP/port

If source port cannot be reliably preserved/used in the required flow, state that clearly and prepare the evidence needed for an HMRC omission request rather than fabricating it.

- Gov-Vendor-Public-IP

==================================================
